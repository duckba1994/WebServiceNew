## 1. หน้าเว็บต่อครบทั้ง 5 ขั้นตาม contract แล้ว

ทุกขั้นเป็น **แท็บใน `RequestDetailModal`** (`CR_STEP_TABS`) ไม่ใช่ route แยก — เหมือน IT / PL

| แท็บ | step | `action` ที่ยิง | ฟิลด์ที่ส่ง | ปุ่มวาดที่ไหน |
|---|---|---|---|---|
| **General** (ไม่มีแท็บอนุมัติแยก) | 1 | `approve` | — | บล็อกปุ่มมาตรฐาน + กล่องยืนยัน |
| รับเรื่อง | 2 | `receive` | `requestService` (บังคับ ≤ 100) | ในแผง (ต้องพาค่าฟอร์มไป) |
| ดำเนินการ | 3 | `saveService` / `service` | `serviceDetail` (≤ 1,000 · บังคับเฉพาะ `service`) | ในแผง |
| รับงาน | 4 | `acceptWork` | — | บล็อกปุ่มมาตรฐาน + กล่องยืนยัน |
| ปิดงานที่แจ้งเรื่อง | 5 | `close` | `actionDetail` (ไม่บังคับ ≤ 500) | ในแผง |

จุดที่ทำตาม contract แบบเฉพาะเจาะจง:

- **ปุ่มทุกปุ่มมาจาก `availableActions`** — `label` / `style` เอาจาก API ตรง ๆ ไม่มี hardcode
  `[]` = แผงกลายเป็นอ่านอย่างเดียวเอง โดยไม่ต้องเดาว่าเพราะอะไร
- **ขั้นอนุมัติไม่มีแท็บของตัวเอง** (ผู้ใช้สั่ง 1 ก.ย. 2026) — ปุ่มอนุมัติอยู่ท้ายแท็บ General
  คู่กับข้อมูลที่ใช้ตัดสินใจ (ส่วนงาน / ประเภทที่แจ้ง / วันที่ต้องการ / รายละเอียด / ผู้อนุมัติ)
  เหมือน IT และ PL · **ห้ามเอา `approve` ไปใส่ `actionCodes` ของแท็บใด** ไม่งั้นปุ่มจะหายจาก General
- **ชื่อฟิลด์ไม่สมมาตร** — ส่ง `serviceDetail` แต่อ่านกลับที่ `resolution.resolutionDetail`
  (เขียนคอมเมนต์กำกับไว้ในโค้ดแล้ว เพราะเป็นจุดที่คนอ่านทีหลังจะแก้ผิดแน่ ๆ)
- **`saveService` ไม่ประทับชื่อ/เวลา** → หน้าเว็บไม่เอา `servicedBy` / `servicedDate` มาโชว์เป็น
  "บันทึกล่าสุด" (จะว่างตลอดทั้งที่บันทึกไปหลายรอบ) ใช้ข้อความ `message` จาก API เป็นตัวยืนยันแทน
- **`service` / `close` / `receive` ต้องกดยืนยัน 2 จังหวะ** ตามที่ guide เตือนว่ากดแล้วย้อนไม่ได้
- **`wfStep` = 6 ทั้งที่มี 5 ขั้น** — `stepText()` ใน `requestListData.ts` เช็ค `wfStep > wfStepTotal`
  แล้วโชว์ป้าย phase แทน จึงไม่มีทางขึ้น "6 จาก 5"
- **404 ภาษาอังกฤษ** (`Entity 'CR Request' … was not found.`) ถูกแปลเป็น "ไม่พบใบแจ้งเรื่องนี้ในระบบ"
  ที่ `throwApiError()` ใน `api/client.ts` (ทางกดปุ่ม) และ `useRequestDetail.ts` (ทางเปิดใบ)
- **`planCompleteDate`** (วันรับเรื่อง + 3 วัน) แสดงแบบอ่านอย่างเดียวทุกที่ และในแท็บรับงาน
  เทียบกับ `servicedDate` ให้เป็นป้าย "ตรงกำหนด / เกินกำหนด"

## 2. 🔴 ยืนยันแล้วว่าพัง — API ไม่ได้ decode `%2F` ในเลขที่ใบ

**อาการ (พบจริง 1 ก.ย. 2026):** กดอนุมัติแล้วได้

```
Entity 'CR Request' with key (BHV-SER01%2F26-0010) was not found.
```

ข้อความนี้บอก 2 อย่าง:

1. **request ถึง controller แล้ว** — ข้อความนี้เป็นของ API เอง ไม่ใช่หน้า error ของ IIS
   → IIS **ไม่ได้** บล็อก `%2F` ปัญหาจึงไม่ใช่ `allowDoubleEscaping` อย่างที่กลัวไว้ตอนแรก
2. **ค่า `docNo` ที่ controller ได้รับยังเป็น `BHV-SER01%2F26-0010`** คือยังไม่ถูก decode
   → ไปค้น DB ด้วยคีย์ที่ไม่มีอยู่จริง เลยตอบ 404

**สาเหตุ:** ASP.NET Core **ไม่ decode `%2F` ใน route value โดยเจตนา** — ถ้า decode มันจะกลาย
เป็น `/` แล้วเปลี่ยนจำนวน segment ของ path ทำให้ match ผิดเส้น (percent-encoding ตัวอื่น
ถูก decode ให้หมด `%2F` เป็นข้อยกเว้นตัวเดียว)

**ฝั่งหน้าเว็บถูกต้องแล้ว ไม่ต้องแก้:** ส่ง encode ชั้นเดียว
`encodeURIComponent("BHV-SER01/26-0010")` → `BHV-SER01%2F26-0010` และ URL ประกอบด้วยการ
ต่อสตริงตรง ๆ (`src/config.ts` → `apiUrl()`) `fetch()` ไม่ได้ encode ซ้ำให้
**ส่ง `%252F` ไปก็ไม่ช่วย** เพราะ Kestrel decode `%25` → `%` ได้ค่าเดิมเป๊ะ — ต้องแก้ที่ฝั่งรับเท่านั้น

**แก้ที่ backend — เลือกทางเดียว**

**(ก) decode ใน controller** ← แนะนำ เล็กสุด แก้ 2 จุด (เส้น detail กับเส้น action)
```csharp
docNo = Uri.UnescapeDataString(docNo);   // "BHV-SER01%2F26-0010" → "BHV-SER01/26-0010"
```
⚠️ decode ครั้งเดียวพอ · เลขที่ใบ CR มีแค่ `A-Z 0-9 - /` จึงไม่มีเคส `%` จริงในข้อมูลให้เพี้ยน

**(ข)** ทำ route parameter transformer / action filter ให้ decode `{docNo}` ทุกเส้นทีเดียว —
คุ้มกว่าถ้าจะมีเส้นอื่นที่รับ jobNo อีก (เช่นไฟล์แนบของ CR ในอนาคต)

**(ค)** เพิ่มเส้นที่รับ `docNo` ทาง query string แทน path

> เส้นที่พังเพราะเรื่องนี้คือ **ทั้ง `GET /Requests/CR/{docNo}` และ `POST …/action`**
> (เปิดใบก็ไม่ได้รายละเอียด/timeline กดปุ่มก็ไม่ผ่าน) — ใบ IT/PL ไม่โดนเพราะเลขที่ใบเป็นตัวเลขล้วน

**ทดสอบว่าแก้ผ่านหรือยัง** — วางใน devtools console ตอนล็อกอินอยู่:
```js
const t = JSON.parse(localStorage.app_user).token, d = 'BHV-SER01/26-0010';
fetch(`https://localhost:44377/api/v1/Requests/CR/${encodeURIComponent(d)}`,
      { headers: { Authorization: 'Bearer ' + t } }).then(r => r.json()).then(console.log);
```
ได้ `item` กลับมา = ผ่าน · ได้ `was not found` = ยังไม่ได้แก้

## 3. 🔴 ต้องยืนยัน — `item.requestDate` ของใบ CR คือวันที่อะไร

`CR-workflow-frontend-guide.md` §2 บอกว่าช่อง **"วันที่แจ้ง"** ให้อ่านจาก `item.requestDate`

แต่ตอนทำฟอร์มสร้างใบ (ยืนยันกับผู้ใช้ 1 ก.ย. 2026) ตกลงกันว่า:

| ฟิลด์ตอน `POST /CRRequest` | ความหมาย | ใครใส่ |
|---|---|---|
| `requestDate` | **วันที่ต้องการ** | ผู้ใช้กรอกในฟอร์ม |
| `jobDate` | DocDate = วันที่สร้างเอกสาร | backend ใส่เวลาปัจจุบัน |

หน้าเว็บจึงส่ง "วันที่ต้องการ" ลงคอลัมน์ `RequestDate` และตัวอย่างใน guide เองก็เป็น
`"requestDate": "2026-09-17T00:00:00+07:00"` ซึ่งเป็นวันในอนาคต — **เข้ากับ "วันที่ต้องการ" ไม่ใช่ "วันที่แจ้ง"**

**ผลถ้าปล่อยไว้:** ตาราง "เรื่องที่แจ้งออกไป / แจ้งเข้ามา" ใช้ `requestDate` เป็นคอลัมน์
*วันที่แจ้ง* + ตัวกรอง `dateFrom`/`dateTo` + การเรียง `sortBy=RequestDate` ทั้งหมด
→ ใบ CR จะเรียงและถูกกรองด้วยวันในอนาคต โดยไม่มีใครจับได้เพราะตัวเลขดูมีเหตุผลทุกใบ

**ที่อยากได้:** ใบ CR ส่ง `requestDate` ← `JobDate` (วันที่แจ้งจริง) และ `planDate` ← `RequestDate`
(วันที่ต้องการ — ฟิลด์เดียวกับที่ PL ใช้อยู่แล้ว หน้าเว็บมีที่แสดงรออยู่)

> ระหว่างรอ: แท็บ "อนุมัติ" ของ CR ติดป้ายค่านี้ว่า **"วันที่ต้องการ"** ตามข้อตกลงตอนสร้างใบ
> ถ้า backend ยืนยันว่าเป็นวันที่แจ้งจริง ๆ ต้องกลับไปแก้ทั้งป้ายนี้และฟอร์มสร้างใบให้ตรงกัน

### 4.1 ฟอร์มแก้ไขใบ CR — ต่อกับ `GET` / `PUT /CRRequest/{docNo}` แล้ว

หน้าเว็บทำตาม `CR-create-frontend-guide.md` §7 ครบ:

- **เติมฟอร์มด้วย `GET /CRRequest/{docNo}`** (ไม่ใช่ `GET /Requests/CR/{docNo}`) เพราะเส้นกลาง
  รวม `requestType` กับ `requestSubType` เป็นข้อความเดียว ผูก dropdown ไม่ได้
  โหลดเส้นนี้ไม่สำเร็จ → **ปิดปุ่มบันทึก** ไม่ปล่อยให้กดทั้งที่ไม่รู้ค่าเดิม (จะเขียนทับด้วยค่าว่าง)
- **เปิดให้แก้แค่ 3 ช่อง** (ผู้ใช้ตัดสิน 1 ก.ย. 2026): `requestSubType` (รายละเอียดที่แจ้ง) ·
  `requestDate` (วันที่ต้องการ) · `requestDetail` (รายละเอียด) + `requestSubOther` ที่โผล่
  เฉพาะตอนประเภท = `"อื่นๆ"`
- **`section` กับ `requestType` เป็นค่าอ่านอย่างเดียว** — guide §7 บอกว่าแก้ได้ แต่เลขที่ใบ
  ไม่เปลี่ยนตาม ใบจะกลายเป็นเลขของชุดหนึ่งแต่เนื้อหาเป็นอีกชุด → **ไม่เปิดให้แก้ตั้งแต่แรก
  ดีกว่าเตือนแล้วปล่อยกด** (เลือกผิดตอนแจ้ง = ต้องเปิดใบใหม่) ฟอร์มโชว์ 2 ค่านี้ไว้ให้เห็น
  พร้อมเหตุผลที่แก้ไม่ได้
- `PUT` ยังส่งครบทุกช่องเสมอ — `section` / `requestType` ส่งค่าเดิมกลับไป เพราะ API บังคับให้มี
  และ `requestSubType` ต้องผ่านการตรวจว่าอยู่ใต้ประเภทนั้นจริง
- `requestSubType` **ไม่ได้อยู่ในสูตรออกเลข** (เลขผูกกับ ส่วนงาน + ประเภทที่แจ้ง เท่านั้น)
  จึงแก้ได้โดยไม่กระทบ running — ตัวเลือกกรองด้วย (`section` + `requestType`) ของใบตามเดิม

#### 🟡 ขอเพิ่มเงื่อนไขฝั่ง backend 2 ข้อ (guide §7 เสนอไว้เองว่าทำได้)

ตอนนี้ `canEdit` ของ API เป็น `false` **เฉพาะใบที่ปิด/ยกเลิกแล้ว** — ระหว่าง step 1-5 ใครก็แก้ได้
รวมถึงคนต่างแผนก ซึ่งไม่ตรงกับที่ผู้ใช้สั่งไว้ (1 ก.ย. 2026):

1. **ห้ามแก้หลัง Mgr ต้นสังกัดอนุมัติ** — แก้ได้เฉพาะ `wfStatus = "Approved-Request"` เท่านั้น
   (อนุมัติแล้วให้ตอบ 409) ไม่งั้นผู้แจ้งแก้เนื้อหาที่ผู้อนุมัติเซ็นไปแล้วได้
2. **แก้ได้เฉพาะคนในหน่วยงานผู้แจ้ง** (เทียบ `departid` จาก token กับของใบ)

> หน้าเว็บบังคับ 2 ข้อนี้ให้แล้ว (ซ่อนปุ่มแก้ไขทันทีที่ใบพ้นขั้นอนุมัติ) **แต่เป็นแค่การซ่อนปุ่ม
> ไม่ใช่การบังคับ** — ใครยิง `PUT` ตรงยังแก้ได้อยู่ จนกว่า backend จะใส่เงื่อนไขเดียวกัน
> และเมื่อใส่แล้ว `canEdit` ควรสะท้อนเงื่อนไขนี้ด้วย หน้าเว็บจะได้เลิกเดาเอง

## 5. เช็คอีก 2 อย่างตอนต่อจริง (นอกจาก §2)

1. **`departmentShort` ของผู้ใช้แผนก CR ต้องเป็น `"CR"`** — หน้า "เรื่องแจ้งเข้ามา" ใช้ค่านี้
   เป็น `module` ที่ยิง `GET /Requests/incoming?module=…` ถ้า token คืนมาเป็นอย่างอื่น
   (เช่น `"11"` หรือชื่อเต็ม) คิวงานของ CR จะว่างเปล่าทั้งที่มีใบรออยู่
2. **`Login.approve` ของบัญชี Mgr ต้อง = 1** ไม่งั้น `availableActions` ของ step 1 จะว่าง
   → ปุ่มอนุมัติไม่ขึ้น (เคสเดิมที่เคยเจอกับ IT)
