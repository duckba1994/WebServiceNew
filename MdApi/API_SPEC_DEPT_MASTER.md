# API SPEC — Master Data ของใบแจ้งเรื่อง HR / GA / IM / AF / SV / SQA / PS

สถานะ (8 ก.ย. 2026): **มีของจริงครบทั้ง 7 แผนกแล้ว** รวมถึงสองเส้นใหม่ของใบประเมิน PS
(`/MasterData/ps/prelims` · `/ps/prelims/{id}`) ตรวจแล้วทุกเส้นตอบ 401 = มีจริง
หน้าเว็บ (ฟอร์มสร้างใบแจ้งเรื่อง) ยิงทันทีที่เปิดฟอร์มของแผนกนั้น แผนกที่ยังไม่มี endpoint
จะขึ้นข้อความ "โหลดตัวเลือกของแผนก X ไม่สำเร็จ" พร้อมปุ่ม "ลองใหม่" ใต้ช่องนั้น
(ไม่มีรายการสำรองในโค้ด — ดู CLAUDE.md) ส่วนชุดที่ยิงผ่านแต่ไม่มีสักรายการ ขึ้นข้อความสีเหลือง
"ยังไม่มีตัวเลือกจากระบบ" แทน — ช่องจะได้ไม่ดูเหมือนเสียเฉย ๆ

### ข้อที่ของจริงต่างจากสเปกนี้ (ยึดของจริง)
- **แถวชื่อว่าง** — HR (`id` 0) และ SV (`id` 1 ทั้งสองส่วนงาน) ส่ง `name` เป็นสตริงว่างมาด้วย
  เป็นตัวเลือกเปล่าหัว dropdown ของเว็บเก่า หน้าเว็บกรองทิ้ง (ช่อง "-- เลือก --" ทำหน้าที่นั้นแล้ว)
- **`id` ซ้ำ/ข้ามเลข** — IM มี `id` 5 สองแถวและไม่มี 6 · SV ใช้ `id` ชุดเดียวกันทั้ง HV/FL แต่คนละเรื่อง
  หน้าเว็บใช้ `name` เป็นทั้ง key และค่าที่บันทึกอยู่แล้ว จึงไม่กระทบ (ห้ามไล่เลข id ใหม่ให้)
- **ห้ามแก้คำสะกด/ตัดช่องว่างของ `name`** — ระบบเก่าเทียบสตริงตรง ๆ (AF "ขอให้ผลิต", HR "ใบเตือน")
  หน้าเว็บส่งชื่อกลับไปดิบ ๆ ตามที่รับมา
- **HR มี `legacyRequestTypes` เพิ่มมา** — ชุดก่อนแตก "ใบเตือน" เป็น "ใบเตือน ปกติ"/"ใบเตือน GPS"
  ใช้เฉพาะตอน **เปิด/แก้ใบเดิม** ที่ `requestType` เป็น "ใบเตือน" เป๊ะ ๆ เท่านั้น ใบใหม่ใช้ `requestTypes` เสมอ
  → หน้าสร้างใบยังไม่ได้ใช้ชุดนี้ และหน้าแก้ไขยังมีแค่ IT/PL/CR จึงยังไม่ได้ต่อ (ทำเมื่อเปิดให้แก้ใบ HR)
- **SV** — เรื่องที่แจ้งแยกชุดตามส่วนงาน หน้าเว็บ disable ช่องนี้จนกว่าจะเลือก HV/FL และล้างค่าเมื่อเปลี่ยนส่วนงาน
- **SQA เป็นลูกโซ่ 3 ชั้น** (ส่วนงาน → ประเภทเรื่องที่แจ้ง → รายละเอียดที่แจ้ง) และชื่อชุดไม่ตรงกับแผนกอื่น:
  ชั้นที่ 2 มาที่ `requestTypes` (ไม่ใช่ `types`) ชั้นที่ 3 มาที่ `requestDetails` (ไม่ใช่ `requestSubTypes`)
  ชั้นที่ 3 หิ้วทั้ง `requestTypeId` และ `requestType` (ชื่อ) มา — **หน้าเว็บ join ด้วยชื่อ + section**
  เพราะ id ซ้ำข้ามส่วนงาน (HV id 4 = "อื่นๆ" · FL id 4 = "อบรมลูกค้า" และ FL เริ่มนับที่ 4)
  ทั้งสองช่องล่างถูกล็อกจนกว่าจะเลือกส่วนงาน รวมถึงช่อง "รายละเอียด" ด้วย ตามของเดิม
- **ประเภทที่ไม่มีรายละเอียดผูกไว้เลยเป็นเรื่องปกติ** (SQA: "การขนย้าย" ของ FL) หน้าเว็บขึ้นข้อความสีเทา
  "ไม่มี…สำหรับตัวเลือกที่เลือกไว้ — ข้ามช่องนี้ได้" **และปลดบังคับกรอกให้ช่องนั้น** ไม่งั้นใบส่งไม่ออก
  (ปลดเฉพาะตอนโหลด master สำเร็จเท่านั้น — โหลดพลาดยังบังคับกรอกเหมือนเดิม)
- **GA/IM** — ช่อง "ประเภท" เปิดฟอร์มมาเลือกตัวแรก ("ทรัพย์สิน") ไว้ให้ ตามพฤติกรรมของเว็บเก่า

## 1. Endpoint

```
GET /api/v1/MasterData/{dept}      dept = hr | ga | im | af | sv | sqa | ps
Authorization: Bearer <token>
```

หนึ่งเส้นต่อหนึ่งแผนก คืน **ก้อนเดียวหลายชุด** (แบบเดียวกับ `/MasterData/it` · `/pl` · `/cr` ที่มีอยู่แล้ว)

## 2. Response

```jsonc
{
  "sections":       [ { "code": "HV", "name": "รถใหญ่" }, { "code": "FL", "name": "รถยก" } ],
  "types":          [ { "id": 1, "name": "...", "section": "HV" } ],
  "requestTypes":   [ { "id": 1, "name": "...", "section": "HV" } ],
  "requestSubTypes":[ { "id": 1, "name": "...", "section": "HV", "typeId": 1 } ],
  "units":          [ { "id": 1, "name": "ชิ้น" } ]
  // ⚠️ ใบประเมินของ PS ไม่ได้อยู่ในก้อนนี้แล้ว — ย้ายไปสองเส้นของตัวเอง (ดูข้อ 4.1)
}
```

- ⚠️ **`sections` ของเส้นนี้ไม่ได้ใช้แล้ว** — ช่อง "ส่วนงาน" ของทุกฟอร์มอ่านรายการ HV/FL
  จาก `GET /MasterData/cr` เส้นเดียว (ผู้ใช้สั่ง 6 ก.ย. 2026: ให้เหมือนของ CR)
  แต่ `section` ที่ผูกมากับแถวอื่น **ต้องเป็นโค้ดชุดเดียวกับของ CR** (HV/FL) ไม่งั้นกรองไม่ตรง
- ชุดไหนแผนกนั้นไม่มี **ไม่ต้องส่ง field นั้นมา** (หรือส่ง `[]`) — ฟอร์มไม่ได้ใช้ชุดที่ไม่ได้ประกาศไว้
- `section` / `typeId` = **ไม่บังคับ** ใส่มาเมื่อรายการนั้นแยกตามส่วนงาน / แยกตามประเภทเท่านั้น
  - ไม่ใส่ `section` → หน้าเว็บแสดงทุกแถวไม่ว่าเลือกส่วนงานอะไร
  - ไม่ใส่ `typeId` ใน `requestSubTypes` → แสดงทุกแถวไม่ว่าเลือกประเภทอะไร
- ⚠️ ถ้า `id` ซ้ำข้ามส่วนงาน (แบบ CR) ให้ส่ง `section` มาด้วยทุกแถว หน้าเว็บกรองด้วย section + typeId เสมอ

## 3. ชุดที่แต่ละแผนกใช้จริง

| แผนก | ฟิลด์ในฟอร์ม | ชุดที่ต้องส่ง |
|------|--------------|----------------|
| HR | เรื่องที่แจ้ง | `requestTypes` (ชุดเดียวที่ HR ใช้) |
| GA / IM | ประเภท | `types` |
| GA / IM | เรื่องที่แจ้ง | `requestTypes` |
| AF | เรื่องที่แจ้ง | `requestTypes` |
| SV | ส่วนงาน (HV/FL) | — (ใช้ `sections` ของ `/MasterData/cr`) |
| SV | เรื่องที่แจ้ง | `requestTypes` |
| SQA | ส่วนงาน (HV/FL) | — (ใช้ `sections` ของ `/MasterData/cr`) |
| SQA | ประเภทเรื่องที่แจ้ง | `requestTypes` (แยกตาม `section`) |
| SQA | รายละเอียดที่แจ้ง | `requestDetails` (ผูกกับ `requestTypes` ด้วย **ชื่อ**) |
| PS | ประเภท | `types` |
| PS | เรื่องที่แจ้ง | `requestTypes` |
| PS | เลขที่ใบประเมินราคา (+ ข้อมูลเครื่องจักรอีก 9 ช่อง) | — (เส้นแยก `/ps/prelims` ดูข้อ 4.1) |
| GA / IM / AF / SV / PS | หน่วยของ "รายการที่ขอ" | `units` (ไม่ส่ง = ใช้ชุดกลางของหน้าเว็บ) |

## 4. กติกาที่หน้าเว็บยึด

- **ค่าที่ฟอร์มเก็บและจะส่งกลับตอนสร้างใบ = `name`** ไม่ใช่ `id`
  (ยกเว้น **ส่วนงาน** ที่เก็บ `code` เพราะเป็นคีย์ที่ชั้นล่างอ้างถึง — เหมือน CR)
- เปลี่ยนส่วนงาน → ล้างค่าชั้นล่างทิ้ง, เปลี่ยนประเภท → ล้าง "รายละเอียดที่แจ้ง" ทิ้ง
- ค่าที่บันทึกไว้แล้วแต่ไม่มีใน master แล้ว ต้องยังแสดงเป็นตัวเลือกที่เลือกอยู่ได้ (ห้ามเด้งว่าง)

## 4.1 ใบประเมินของ PS — สองเส้นแยก ไม่ใช่ master ที่ cache ได้

ข้อมูลชุดนี้มาจากวิวของ **ฐานระบบซ่อม** (คนละฐานกับใบแจ้งเรื่อง) และงานซ่อมเดินตลอด
หน้าเว็บจึงโหลดใหม่ทุกครั้งที่เปิดฟอร์ม ไม่เก็บข้ามวัน

```
GET /MasterData/ps/prelims?search=SBF26&take=50   → ["IB2505085", "SBF2609013", …]
GET /MasterData/ps/prelims/{id}                   → รายละเอียดใบเดียว
```

- รายการเป็น **อาร์เรย์ของสตริง** (เลขที่ใบล้วน ๆ) เฉพาะใบที่ยังเปิดอยู่ ราว 800 รายการ
  หน้าเว็บยิงครั้งเดียวตอนเปิดฟอร์มด้วย `take=5000` แล้วกรองฝั่งหน้าเว็บ (คอมโบบ็อกซ์เรนเดอร์สูงสุด 100 แถว)
  ถ้าวันหนึ่งใบทะลุ 5000 ค่อยเปลี่ยนไปค้นฝั่ง server ด้วย `?search=` ตอนผู้ใช้พิมพ์ — ไม่ต้องแก้รูปฟอร์ม
- **ชื่อ field ของรายละเอียดเป็นภาษาของระบบซ่อม ไม่ตรงกับป้ายบนฟอร์ม** คู่ที่ถูกต้อง (อย่าเดาเอง):
  `prelimDate`→วันที่ · `carType`→ประเภทเครื่องจักร · `carEngineNo`→รุ่นเครื่องยนต์ ·
  `carSerial`→ทะเบียน S/N · `carId`→หมายเลขเครื่องจักร · `carModel`→รุ่นเครื่องจักร ·
  `groupName`→ระบบ · `subGroupName`→รายละเอียดอาการ · `reComment`→รายละเอียดเพิ่มเติม
  (อยู่ที่ `prelimToFields` ใน `hooks/usePsPrelims.ts` ที่เดียว)
- ค่าที่ฟอร์มเก็บและจะส่งกลับตอนสร้างใบ = **เลขที่ใบ** เท่านั้น อีก 9 ช่องเป็นข้อมูลแสดงผล
  (ตอนทำ endpoint สร้างใบ ไม่ต้องรับ 9 ช่องนั้นกลับ — อ่านจากใบต้นทางฝั่ง DB ได้เลย
  เช่นเดียวกับ `carIdStarAcc`/`ncrNo` ที่เว็บเก่าซ่อนไว้แล้วใช้ตอนบันทึก)
- ทุก field ยกเว้น `prelimId` เป็น **null** ได้ (ใบที่ยังไม่ได้ประเมินยังไม่มีข้อมูลเครื่องจักร)
  `prelimDate` เป็น ISO หน้าเว็บแปลงเป็น dd/MM/yyyy ให้
- **ค้นหาได้เฉพาะเลขที่ใบ** — ข้อมูลเครื่องจักรอยู่คนละเส้น จึงยังไม่มีตอนที่ยังไม่ได้เลือกใบ
- เลือกใบใหม่ทับทั้งชุด, ล้างตัวเลือกก็ล้างทั้งชุด และหน้าเว็บทิ้งผลที่มาช้ากว่าใบที่เลือกล่าสุด
  (กดเปลี่ยนใบรัว ๆ แล้วข้อมูลของคนละใบจะไม่ปนกัน)
- ใบที่ไม่มีในระบบได้ **404** → ขึ้นข้อความ "ไม่พบข้อมูล ID : xxx" ใต้ช่อง ตามของเดิม

## 5. ยังไม่มี (ทำต่อเมื่อ backend พร้อม)

- **endpoint สร้างใบ** ของ HR / GA / IM / AF / SV / SQA / PS — ตอนนี้กด "ส่งใบแจ้งเรื่อง" แล้วขึ้นหน้าสรุปอย่างเดียว
  ยังไม่ได้ยิง API (แบบเดียวกับที่ IT/PL/CR เคยเป็นก่อนมี endpoint)
- **endpoint แนบรูปของ SV** (`ImgPath1..3` แบบ IT/PL) — ฟอร์มมีช่องแนบรูป 3 รูปแล้ว
- ฟิลด์ที่ยังไม่มีที่เก็บฝั่ง DB: `customerType` (ลูกค้าภายนอก/ภายใน) + `customerDept` (แผนกลูกค้าภายใน)
  และ `attachedDocs` (สิ่งที่แนบมาด้วย — ติ๊กหลายข้อ) + `attachedOther` ของ SV
- PS: ต้องยืนยันว่า **"Plan วันที่ต้องการราคา"** ผู้แจ้งกรอกเอง หรือฝั่ง PS เติมทีหลัง
  (ตอนนี้ทำเป็นช่องไม่บังคับในฟอร์มผู้แจ้ง)
